三、与队友的明确边界

我们负责：地图交子、官方地点印章、个人自制章、积分账户与流水、成长等级、商品兑换、兑换订单、工作人员核销、纪念图导出。

队友/公共服务负责：统一用户登录、活动与地点/商户目录、AI 路线生成、真实定位打卡验证、真实消费确认、文化体验核验。不要替队友开发这些系统；本模块只接收经过验证的业务结果。

保留 userId、activityId、placeId、merchantId、routeId、taskId、orderId 等统一标识的适配位置。登录用户由服务端可信会话获得，不能相信用户端传入的 userId、任意加分值或 verified=true。

接入以下受信任服务端事件，具体字段沿用总体方案：
- checkin.verified
- purchase.verified
- culture_task.completed
- route.completed

每个事件有 eventId、业务来源编号和来源鉴权；服务端根据本模块配置决定奖励，做请求幂等与业务来源去重。真实接入留给联调，但现在就实现可调用的事件入口和契约文档。

上游尚未完成时，通过服务端的 demo adapter 模拟已核验事件，页面标注“演示”。演示入口和测试身份仅在显式 demo 配置中启用；正式配置下关闭。任务页“去打卡/去消费”的正式行为调用宿主跳转适配器；未接入时给出明确提示，演示动作使用独立、清楚标记的入口。

四、图片没准备好时如何实现

1. 建立集中式素材映射，例如 asset-manifest。用 B01、C01—C05、D01—D03、E01—E05 等逻辑编号对应实际运行素材、占位素材与来源标记。页面组件不散落硬编码素材路径。
2. 先用 WXSS、Canvas、小型本地占位 PNG 或现有一致的图标做出完整界面；地点章和商品占位需要能区分，并标记“示意”或“素材待替换”。不要显示破图，也不要把占位图说成真实商品照片或 AI 结果。
3. 所有成长阶段共用 B01 底图；升级装饰、标题、编号、印章与名称均由代码独立绘制，不依赖四张像素对齐的整卡图片。每页六章、三列两行，超过后自动分页，按同一份归一化布局配置驱动展示和 Canvas 导出。
4. 真实图片之后放进 assets-source/。提供导入/压缩脚本或明确替换步骤，将它们转换为分包内运行素材，或接入团队文件服务；只调整素材映射/导入配置，不修改业务流程。不要直接把所有生图原始大图打进小程序主包。
5. 为图片加载失败设置组件级回退；导出纪念图同样支持占位或代码绘制，不能页面正常但 Canvas 因素材缺失整体失败。远程图片进入 Canvas 前通过小程序能力下载并处理失败。
6. A02—A08 不需要等待长屏 UI 图，按 Flova 适配文档的页面布局与公共视觉规格实现。暖纸色 #F8F4E9、朱红 #B83A32、墨色 #2B2926、竹青 #496C5C、柔和金色 #B7985A；保证手机端可读与点击区域，不做成一张不可交互的海报。
7. WorkBuddy + Flova 当前负责离线静态素材。不要假设该连接器可直接被小程序调用。用户实时照片识别/制章通过独立服务端 AI 适配器接入；未配置时运行明确标记的示例模式。
8. 不在本任务中启动 Flova 生成或修改其权限。也不删除、覆盖或批量提交另一窗口正在产出的素材与反馈文件。

五、必须遵守的产品规则

- 一位用户在一个活动中只有一张持续成长的地图交子；地点章按地点去重，自制章按生成任务去重。每页六个位置，自动翻页，已有章和添加顺序保持。
- lifetimePoints 是累计成长积分，availablePoints 是可用余额；兑换只扣可用积分，取消或到期只退可用积分，不制造累计成长积分。正常兑换不掉级、不删除印章。
- 等级门槛为 0/100/300/600；累计 600 分自动解锁数字纪念交子，不扣分。固定实体纪念卡需要累计达到 600，再花 200 可用积分兑换；数字解锁、可兑换资格、实体订单状态分别表达。
- 初始领取 +20、每日签到 +10、有效地点 +40、消费 +60、文化体验 +60、路线完成 +80；频次、每日上限、不同业务去重和上海时区日期按总体方案完整实现。超过地点奖励日上限仍可以记录新的官方章，但不补发该地点积分。
- 五类演示商品按 60/120/180/200/300 积分配置。兑换需校验余额、库存、纪念资格、活动期和个人限制，事务内创建订单、扣分、预占库存，重复提交不能多扣分。
- 订单状态 PENDING/REDEEMED/CANCELLED/EXPIRED。未核销订单取消或超时退分并释放库存一次；核销不再次扣分；并发取消、超时和核销只能有一个转换成功。到期在服务端读取与操作时也处理。
- 动态兑换码默认 5 分钟，待领取订单默认 15 分钟；码过期不等于订单过期，刷新码让旧码失效。使用真实 token 和可解码的二维码方案，不能用装饰性假二维码。核销有独立工作人员与兑换点权限。
- 自制章流程：选择照片 → 识别 → 用户确认/修改主题 → 生成 → 预览 → 确认添加。始终不加分，不作为真实打卡证明；未配置真实 AI 时明确显示“示例模式”，使用可用示例图，不声称依据照片实时生成。
- AI 识别与生成经服务端调用，密钥只放服务端环境。任务状态、失败重试、每日成功次数与幂等按总体方案执行；同一结果不能重复添加。
- 不做自由拖拽缩放、反向路线推荐、个性实体卡、真实支付、区块链或完整运营后台。

六、要交付的页面与顺序

先贯通纵向流程，再补齐细节，不能只写七个彼此断开的页面：
1. 我的交子：领取、六章分页、等级进度、两种积分、纪念状态、改名与各入口。
2. 任务页：签到、地点/消费/文化/路线任务，状态与上限提示，宿主跳转和演示事件入口。
3. 积分明细：获得、兑换扣减、退款、来源时间和分页。
4. 兑换中心与兑换记录：商品、库存、条件、确认兑换、待领取/已领取记录。
5. 订单详情：真实动态码、倒计时、刷新、取消、核销后状态。
6. 工作人员核销：工作人员鉴权、扫码/测试码输入、确认领取、重复码和错误码反馈。
7. AI 自制章：选择照片、确认主题、生成状态、预览、添加、失败与示例模式。

优先做账户/积分/章 → 成长 → 兑换与核销 → AI 完整交互；主卡展示、占位素材和服务端同步迭代。核心流程跑通后补改名、Canvas 纪念图导出及轻量盖章/升级反馈。

后端必须持久化积分、印章、库存、订单与任务，重新启动仍能恢复，不能只靠前端 localStorage/小程序缓存假装完成。demo 与正式适配应复用同一套规则和事务，不维护两套互相矛盾的业务实现。

八、Git 与多窗口协作

开始前检查分支、已有修改和 worktree，保留用户及其他窗口的文件，不做覆盖式 reset/clean，不自动 stash 整个工作区。

默认在 codex/digital-jiaozi 开发。如果该分支已在另一 worktree 使用，或者发现另一个窗口正在同目录写代码，使用 D:\Codex\ 下独立 worktree 和从该模块分支派生的 codex/digital-jiaozi-impl（重名则用合理后缀），不要抢切另一窗口的分支。新 worktree 需要包含本交接和已有方案；未提交的参考资料按需复制，不能从旧工作区搬走。

按功能分批提交，只暂存自己本轮修改且已检查的明确文件；不要 git add . 把另一执行端的未跟踪图片、反馈或其他成员变更一起提交。遵守已有模块分支协作方式，可正常推送本模块开发分支，不强制推送，不合并 main。最终给出分支和提交信息，方便队内审阅后联调合并。

普通实现细节自行判断并记录；上游接口未确定时先定义可替换契约和演示实现继续开发。只有确实影响公共契约或需要必要凭据时再提出具体问题，不能因此停止不依赖该问题的其他工作。

先简短说明你检查到的目录、当前分支和首个实现步骤，然后开始编码，持续做到模块可运行并交付验证与接入说明。
