# Flova 执行适配与问题答复

日期：2026 年 10 月 31 日

适用范围：WorkBuddy 通过连接器调用 Flova，为 Jiaozi-Trail 微信小程序数字交子模块准备图片。

初稿依据：用户提供的《生图执行端反馈-Flova实测与待裁决问题》，以及本模块的总体方案与原始图片清单。

探针后更新：已收到《Flova探针实测回执》，并本地查看 B01、C01 小尺寸预览与熊猫对比图，复验交付文件的尺寸、格式及 C01 真实 Alpha。最新处理口径见 [Flova 探针回执答复与后续执行口径](Flova探针回执答复与后续执行口径.md)。Flova 工具调用过程仍依据执行端回执；本窗口没有直接调用 Flova。

本文补充原始清单的执行约定，按当前通道调整生图任务。原清单的 39 个编号继续保留，便于定位提示词和素材路径；它们是候选资产清单，不再作为 39 个必须逐张串行执行的任务。涉及执行数量、尺寸、透明处理、母版一致性和批次时，优先采用本文。

## 一 对反馈的判断

主要问题成立：原清单给出了期望的素材规格，但没有充分定义 Flova Agent 输出如何变成小程序可以使用的资产。应补上资源映射、下载、后处理和验收流程，并把几何准确性移到开发代码中保证。

原清单已经允许同比例原生输出、白底后抠图，并区分优先与后补任务，因此不是所有要求都必须由生成接口直接满足。但“后续处理”没有指定负责方、输出规则与失败处理，确实会让执行端无法闭环。这部分由本答复补齐。

以下判断需要修正：

- 不能仅凭缺少参数就认定必须更换生图平台。Flova 可以负责视觉创作，确定的尺寸、透明化、排版与文件名可以在本地处理。
- 不能把长屏 UI 描述成“物理上做不到”。不同模型和扩图流程的能力不同；当前通道没有可靠保证即可，不需要下绝对结论。本次不依赖这类长屏稿来开发。
- PNG 存在 Alpha 通道，不代表像素真的透明；所有 Alpha 都是 255 的 PNG 仍然完全不透明。调色板 PNG 也可能通过 tRNS 保存透明信息，不能只看 color type。
- 四个阶段的印章位置应由代码定义。即使有原生图生图、尺寸和 seed 参数，也不能把像素对齐当作模型的保证。
- 透明素材共 17 张，其中圆章 C01—C10 与 D01—D03 是 13 张，F02—F05 是 4 张彩色插画，两类需要不同的抠图处理。它们不全是单色印章。

## 二 Q1 尺寸如何处理

接受按可用原生尺寸生成，再由本地后处理得到目标素材。原清单尺寸表示期望导出尺寸，不是对 Flova 隐藏模型参数的要求。

规则如下：

| 素材 | 生成要求 | 本地处理 |
| --- | --- | --- |
| B01 数字交子 | 优先横向 3:2，标题和集章区保持干净 | 保持比例等比缩放；比例偏差时优先扩展纸底或补边，不能裁掉边框 |
| B05 实体卡设计 | 优先横向 3:2 | 保留完整图案，必要时等比放入 3:2 画布 |
| C、D 圆章 | 优先正方形，主体完整、四周留白 | 提取透明主体后放入正方形画布，统一主体大小 |
| E 类商品、G01 | 优先正方形，主体完整 | 允许裁去空背景，不裁商品、金属连接件或角色 |
| A01 风格板 | 4:3 或平台可用横向比例 | 作为参考保留原生尺寸，不强制二次插值 |
| F01 横幅 | 优先宽横图，图案位于边缘 | 保持主体完整后裁剪或补纸底，不能把正方图强行压成 3:1 |
| F03、F04 彩色插画 | 优先正方形 | 先分离主体，再居中放置，不拉伸角色 |

缩小优先使用 Lanczos；只有确实需要时才等比放大，放大不视作补回真实细节。若放大后小程序实际显示尺寸仍模糊，重新生成；不靠文件尺寸宣称高质量。

最终验收以小程序实际显示为准：卡片约 686 rpx 宽，圆章需按下文章位配置扣除名称区后，以实际图案尺寸复验；96 px 预览只作辅助，不能代替六章主卡实排。标题区和盖章区不得出现杂纹与遮挡。保留原始输出，另外保存处理后的版本，避免反复覆盖和重复压缩。B01 探针的 1264×848 可以等比 contain 到 3:2 容器，轻微空隙由同色底承接，不拉伸、不裁边框，也不因此重生成。

## 三 Q2 透明素材由谁处理

当前生成任务由 WorkBuddy 执行，因此下载、文件格式检查和本地预处理也归执行端完成；接手开发的 Codex 负责导入后在小程序中复验。此处是工作分工建议，不表示本会话已经完成处理。

### 3.1 单色圆章的首选兜底

对 C、D 圆章，默认把原提示词中的“透明背景”改为：

```text
请输出单一朱红主体和完全纯白背景。背景必须干净，没有阴影、纸纹、灰色棋盘格、米色底和渐变。主体图案及圆框完整，保留四周约 10% 空白。使用简洁的块面与中粗轮廓，保留清楚的白色镂空，不加密集细线，不生成文字。后续会在本地把白色区域转换为透明，因此不要添加白色实体装饰。
```

如果 Flova 已输出实际有效的透明图，直接保留，不重复抠图。

白底单色章可用 Python Pillow 或 Node.js sharp 处理；执行端检查已有环境后选择，不需要调用另一家生成 API。前景统一为朱红 `#B83A32`，白底作为透明区，抗锯齿边缘使用连续 Alpha，不采用“低于某灰度全部删除”的粗暴硬阈值。

实现建议：对像素颜色 C、目标朱红 F 和白色 W，在统一颜色空间里估计 `alpha = clamp(dot(W-C, W-F) / dot(W-F, W-F), 0, 1)`，RGB 写入目标朱红，Alpha 保留连续变化。它适用于白底单色章；先检查原图是否确实接近白色与朱红的混合，不把彩色图、灰底图或复杂阴影图强行套进该公式。

近零 Alpha 噪点检查与压制纳入标准流程。C01 探针使用 8 位 Alpha 的 `floor=6` 清除极弱背景残留，主体抗锯齿仍保留连续 Alpha；该值是可调默认值，后续逐图检查，不保证适用于所有素材。不进行会啃掉细线的腐蚀操作。若原图有棋盘格、多色、复杂底纹或大片非白阴影，优先重新生成干净白底版。已有有效透明的图片直接保留；不得在忽略原 Alpha 的情况下对 RGBA 成品再次套用白底反解。

带建筑的章追加可数约束：每栋主要建筑最多 3 行、每行最多 3 个窗格开口，不画密集格栅、砖缝和小字招牌。美食、人物章按主体减少配件和纹理，不机械套用窗格规则。接受 C01 的块面结合轮廓方向，以小尺寸辨认为验收标准；具体公共提示词见探针答复。

### 3.2 彩色熊猫插画

彩色插画中的熊猫本身有白色区域，不能套用单色圆章的去白公式，也不能全局删除所有白色像素。

F03、F04 若需要透明，先生成与主体分离清楚的纯色背景，再使用主体分割、边缘连通背景处理或已有抠图工具，保留熊猫白色身体。没有可用分割链路时，生成与页面相同的暖纸色平底版本，限制在同色容器使用；它不能被标记成真透明素材。

### 3.3 透明验收

- 实际解码图片，检查 Alpha 的最小值、最大值及透明像素分布；不能仅看扩展名、文件 color type 或是否有 Alpha 通道。
- 外围空白确实透明，主体主要线条清楚，抗锯齿边缘有过渡；不能整张全透明或全不透明。
- 分别叠加到白底、交子纸底和深竹青底预览，检查白边、黑边、背景残留和细线损坏。
- 缩小到实际印章尺寸复验，不能只在原始大图上看细节。
- 如果采用暖纸色不透明插画，清楚记录 `backgroundMode: opaque-paper`，不要谎报 Alpha 合格。

## 四 Q3 一致性如何保证

采用“代码保证坐标，参考图帮助风格”的组合，核心选择接近反馈中的方案 b，但不再独立生成四张整幅数字底图。

1. B01 是共同底图，供所有成长阶段共用。
2. B02、B03、B04 从 Flova 必做清单移除，由小程序 WXSS 或 Canvas 绘制不同颜色、线宽和角部装饰，导出纪念图时使用同一份布局配置。
3. 印章、标题、编号与阶段文字均为独立图层，不嵌进生图底图。
4. 确定卡片宽高比为 3:2，章位由归一化坐标定义，卡片缩放时整体等比换算。
5. 为避免 B01 自带装饰与代码边框冲突，生成时只保留细且克制的共同边框；升级边框在外缘叠加，不覆盖中央集章区。

建议六个章位使用两行三列，每个单元含图案和代码绘制的名称。以下为归一化单元框，开发时由同一配置驱动页面与 Canvas 导出：

| --- | ---: | ---: | ---: | ---: |
| 第一行左 | 0.07 | 0.215 | 0.24 | 0.25 |
| 第一行中 | 0.38 | 0.215 | 0.24 | 0.25 |
| 第一行右 | 0.69 | 0.215 | 0.24 | 0.25 |
| 第二行左 | 0.07 | 0.535 | 0.24 | 0.25 |
| 第二行中 | 0.38 | 0.535 | 0.24 | 0.25 |
| 第二行右 | 0.69 | 0.535 | 0.24 | 0.25 |

以上按 B01 探针中央干净区更新，替换旧版的 y=0.21/0.55、h=0.30。坐标相对完整的 3:2 票面容器，主体图案与其下方的名称都必须包含在单元框内；先给文字和间距留出高度，再计算正方形图案尺寸，不以宽度直接决定章图高度。页面与 Canvas 导出共用同一份配置，并采用相同的底图等比放置方式，不要求生成模型精确对齐这些坐标。

C01 仍作为圆章风格参考；G01 可作为熊猫插画参考；B05 可作为 E04 实体卡商品图参考。参考链路值得验证，但不再是所有核心图片和小程序布局的硬依赖。

执行端先尝试同项目内引用已生成的 Asset 或资源。如果平台确实支持直接复用，应以工具定义和实测为准；不要仅因 `files` 接受 file_ref 就推断内部资源一定可用。确实需要本地参考图时，再验证 ticket → 字节上传 → complete 链路，严格按票据返回的 transport 上传，不臆造 URL、方法或请求头。

链路失败时记录限制，以统一提示词生成并通过本地色彩、圆框尺寸和布局归一化控制整体观感，不必把整批任务全部停住。

## 六 Q5 UI 改成开发规格

保留用户希望有明确 UI 设计的要求，但不要求执行端生成七张长屏图。UI 设计通过布局、字号、间距、状态和组件规则交接，由开发者在小程序中实现后截图验收。

### 6.1 公共视觉与布局

- 以 750 rpx 作为响应式布局基准，左右留白 32 rpx，常规区块间距 24 rpx。
- 页面主标题约 40 rpx，区块标题约 32 rpx，正文 28—30 rpx，辅助说明约 24 rpx；主要数值可适当更大。
- 主按钮高约 88 rpx，点击区域不小于 88 rpx；同屏主要操作明确，避免多个同等强调按钮。
- 页面底色暖纸色，正文墨色，主要操作朱红，竹青用于辅助或完成状态，柔和金色用于纪念阶段。
- 优先使用可读的系统字体；装饰纸纹只放在票面和少数页头，不铺满输入框、任务列表与积分明细。
- 微信原生导航与胶囊区域由系统及适配布局处理，不在生图里烘焙；底部操作区考虑安全区。
- “我的交子 / 任务 / 兑换”是模块入口，是否进入全项目 tabBar 由团队统一安排，不能擅自替换全项目导航。

## 七 Q6 资源命名与落盘

接受 Flova 先按资源 ID 生成和下载，再在本地映射到清单路径。固定路径是最终整理要求，不是对 Flova 原始资源命名的要求。

执行端必须记录来源，不单靠视觉猜测：

1. 每次任务在文字输入中明确清单编号与名称，例如 `C03 宽窄巷子印章`。按探针回执，普通请求使用 `content`；带参考图时将文字和 `resource_ref` 同放 `parts`，不同时传 `content` 和 `parts`。
2. 记录项目、run、产出节点和 resource ID 与清单编号的对应关系；同一编号有多个候选时全部保留，显式标记选中项。
3. 原始下载放入 `assets-source/flova-raw/<run-id>/`，不覆盖原始文件。
4. 只有确认映射后，才复制并转换为原清单指定的 `cards/`、`stamps/`、`products/` 等路径。
5. 不把 JPEG 或 WebP 直接改扩展名为 PNG；需要时真实解码后重新编码。
6. 缺失映射的资源保持 `UNMAPPED`，不自动按文件排序或相似外观分配到某个地点。

此例不代表已有真实图片；执行后填写真实测量值，并保留候选版本和处理记录。C 类的视觉识别特征已在首批表列明，只能用于复验，不能代替资源溯源。

## 八 Q7 批次与权限

### 8.1 允许一个 run 请求多个独立资源

取消“一张图必须对应一次 run”的执行限制；保留“每个编号最终需要一个独立可用文件”的交付要求。

先运行探针，再按依赖分组，每批建议 2—4 张；这个范围是操作建议，不代表已验证平台支持固定数量。每个结果独立标识编号，不能用一张四宫格作为多个资源交付。

如果 Flova 把请求合成了拼图，先在该 run 中要求拆成独立资源；仍不能做到时，后续降为一 run 一个编号。不要仅切开格子就算交付，以免错配、文字残留或分辨率不足。

### 8.2 full_access 不由本答复代用户授权

这是 Flova 项目的运行权限设置，应由用户对 WorkBuddy 明确授权。用户提供反馈让 Codex 阅读，不等于批准改变该设置；执行端文档中的“额度充足”也不替代权限授权。

建议先保持现有权限模式完成少量探针，记录实际暂停原因和次数。是否切换 full_access，由用户在执行端确认后处理；不需要为此停止编写规格、整理提示词或检查本地素材。

若用户之后授权，授权范围应只涵盖本项目的图片生成、查询、下载与本地处理；不扩展为发布、视频导出、修改其他项目或无关操作。模型不提供该粒度时，执行端仍应自行遵守任务范围。

## 九 探针计划与失败处理

认可先跑 B01、C01、G01 的思路，补充以下要求：探针同样应先记录资源映射；如当前会话尚未被授权创建项目和生图，由用户在 WorkBuddy 下达执行指令后开始，不把这份答复当作操作命令。

| 探针 | 必须记录的事实 | 不阻塞的部分 |
| --- | --- | --- |
| B01 | 实际尺寸与格式、比例、标题和集章留白、是否画入文字、资源 ID | 不要求恰好原生 1536×1024 |
| C01 | 原始背景、真实 Alpha 像素情况、白底透明化结果、小尺寸预览 | 没有原生透明并非失败，白底可处理即通过 |
| G01 | 熊猫外形、比例、小尺寸辨认、资源 ID | 它不是积分与集章业务的硬依赖，失败可以后补 |

另用一张已生成探针图，验证一次同项目参考复用或本地上传链路。只读回已生成的三张图不能证明图生图输入可用，需要实际执行一次带参考的请求并记录输入输出资源关系。

建议每个失败编号先做一次定向修正，再走明确兜底，避免无目的重复生成。该策略为了控制交付时间，不设置额度上限。

### 必须有可用结果，可以换实现方式

- B01：保留交子主视觉。生图始终无法保持留白时，使用纯纸纹底和代码边框制作可用底图，后续再替换装饰。
- C01—C05：五个首批地点需要可区分的章图。优先修正、再透明化；确实无法获得可用图时，可由开发者制作简单线描图章，并标记为临时素材，不能把同一章换五个名称冒充五种设计。
- E01—E05：兑换页面必须能区分商品。生成失败可用清楚标记的临时商品示意。E04 可直接把 B05 合成为卡片效果，无须模型重新发明图案。

### 失败可后补，不阻塞业务

G01、A01、F01、F03、F04 以及未纳入首批的装饰素材。角色不稳定时，先不用角色插画，保持颜色与排版一致即可。

D01—D03 仅为可后补的风格示例，不阻塞真实照片章功能。使用时标注示例来源，不能声称它是程序实时处理用户照片的结果。
